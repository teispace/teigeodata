Install

Add teigeodata to a project in your language, and read the results a query returns.

teigeodata is one Rust engine with a binding for each language, generated from one definition: the calls, their arguments and the columns they return are the same everywhere. Pick your language; every page of these docs remembers it.

Add the package

teigeodata is written in Rust, and Rust gets the engine itself: typed places, typed IDs and points, and queries that write into buffers you reuse, so a warm query allocates nothing. Every other language reaches the same engine through a generated binding.

The crates on crates.io: teigeodata-core, -engine, -sync (the store), -api, -server, -cli (tgd) and what they need, all at the same version.

The minimum Rust version is the one rust-toolchain.toml pins. teigeodata-engine's default features read packs from files (mmap); teigeodata-sync adds the store (download, verify, update); the core crates build for no_std targets.

Registries

Every release is published to crates.io, PyPI, npm, Maven Central, pub.dev and the Go module proxy from CI, by trusted publishing, with provenance where the registry records it. Swift installs from the release tags; C from the release archives. The .NET package is built and tested but not yet on NuGet: build it from a checkout.

Get a pack

Queries read packs: signed, memory-mapped files of places. The examples use the world lite pack: the world's countries, first-level units and cities of 5,000 or more, India's districts and statutory towns, and Nepal in full, 172,339 places named in Nepali, Hindi and English (15.6 MB, CC BY 4.0):

Which pack to choose, and how an app ships or downloads one: packs and the store.

Read a result

Every query returns its rows as one result blob: compact columns in a single buffer, read in place without copying. Each language's reader turns a row into its own natural type and a null into its own null:

The Rust engine returns typed values, not result blobs: a Place holds its ID, kind, admin level and point, and the rest (its name, ISO code, elevation, timezone) is read on demand from the engine, into a buffer you pass. The tour gathers what it prints in one helper:

Queries that return several places write into a Vec you own and reuse (hits, near, places in the tour), with a Scratch for the search's working memory. Points are fixed-point (Point<E6>, Point<E7>): Point::from_degrees checks the range once, so a query never sees an invalid coordinate.

If you want the same blobs every binding gets, teigeodata-api wraps this engine with the binding API (Engine::search returning a result blob).

Names in your language
